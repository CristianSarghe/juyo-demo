# Interface purpose

Prioritize simplicity and ease of use. Keep only task-relevant content: clear actions, questions, answers, and supporting data. Avoid promotional copy, repeated labels, generic AI phrases, and controls without useful behavior.

The application pages are Overview, Room management, Reservations and Hotel configuration. Data schema and Costs & facilities are removed; legacy query links fall back to Overview. Keep shared cost/facility facts and schema metadata needed by remaining features, Kassandra and fixture validation.

Dashboard is the index route `/`; sidebar pages use `/rooms`, `/reservations` and `/hotel-configuration`. Room management is a routed layout with its own child outlet: `/rooms` renders Rooms and `/rooms/prices` renders Room prices. Shared shell/workspace layouts own router outlets and lazy page components own their contents. Use RouterLink and path-based active matching so links support deep links, refresh, browser history and new tabs. Query parameters belong to pricing filters and one-time context, not page identity. Preserve legacy `/network?view=…`, `/room-prices` and `/chat` redirects, and resume validated internal deep links after sign-in.

The login screen contains only the Juyo logo, email and password fields, sign-in controls, and necessary validation states. Keep the page background flat and quiet, with thin offset contours and small purple edge accents confined to the form surround. Decoration must remain noninteractive, hidden from assistive technology and adapted to narrow screens; do not add full-page connection paths, promotional illustrations, text, or a demo action.

# Hotel network data

The application manages a fictional four-hotel network with 88 physical rooms: Brussels 24, Amsterdam 20, Berlin 28, Porto 16. The complete calendar covers every day from October 1 through December 31, 2026. Reservation nights are the source of occupied/booked room nights, room revenue and channel totals; daily room states, costs and facility activity cover the same calendar. Keep static facilities and room-type metadata separate from daily activity. Per the user's latest preference, do not show DEV, development, demo, or test-data labels in the interface or property names. Keep fixture provenance documented in README and machine-readable metadata; preserve stable hotel IDs. Use the canonical network fixtures and selectors for UI and chat calculations. Keep the schema and exported JSON synchronized with `npm run data:export`; run `npm run test:data` after data changes. Use Apache ECharts for every chart.

# Interface design guide

Warnings use generic empty-state wording: No warnings, or No warnings for this location when a hotel is selected. If that hotel has none but the portfolio has warnings, show a separate section with the network warning count and View all warnings. This action selects All hotels through the shared hotel store and immediately shows the full warning list in the same popover, with focus moving to its first item. Hide this action when no warnings exist anywhere.

The authenticated shell owns a shared horizontal toolbar: Juyo logo at far left, Warnings and Upcoming events actions at the right beside the user widget, and the user widget at far right. Both notification actions open Taiga popovers with brief lists; only selecting a row opens an accessible detail modal. Keep Escape/outside dismissal and logical focus return. Their lists follow the selected hotel scope and current business date, independently of analytics date filters. With one hotel selected, toolbar badges show selected count / network total; portfolio scope shows only the total. Warning totals include local room-operation changes. Event totals count unique upcoming/ongoing events, not the sum of per-hotel relevance records. Warnings list actual dated out-of-service rooms; a room detail includes maintenance notes and a View room action. Events list ongoing events first, then future events by nearest start date, showing date and importance. Event detail includes the local geographic map, per-hotel relevance and straight-line distance, and a distinct Kassandra assessment using concise “We think… because…” wording. Keep map assets local with their required attribution, keyboard zoom/pan and fit controls. Room price updates change local daily selling rates; existing reservations and booked revenue retain their original rates. Do not claim a published PMS update; fixture event assessments remain distinct from live chat analysis. The sole global hotel selector belongs in the toolbar, immediately beside the Juyo logo, on every authenticated page. It controls Dashboard, Room management, Reservations, Hotel configuration and chat. On narrow screens it may use a full-width second row. Never duplicate hotel selectors in page headers. Room management and Hotel configuration require one hotel: when the global scope is All hotels, replace their contents with a clean white selection screen asking “What place do you want to see data for?”. Its hotel dropdown is a local draft; Continue commits the choice to the global selector and reveals the page. Changing the toolbar back to All hotels restores this selection screen. Reservations and analytics still support portfolio scope. Clicking the user widget opens a Taiga UI menu containing Log out; do not show a separate logout button in the toolbar or duplicate the account in feature headers or the sidebar.

Hotels and events have WGS84 latitude/longitude coordinates. Events are normalized separately from hotel-event assessments; each relevant hotel has its own mild/medium/important rating, reason, distance and assessment provenance. A shared event appears once in a portfolio list, with all relevant hotel assessments. The current twelve events and thirteen assessments are fictional fixtures; keep provenance in README and metadata, and do not claim that live Kassandra analysis or verified event listings are connected. The `kassandra` assessment source is reserved for future integration. Keep these collections, coordinate bounds and event enums available in the MCP data dictionary and exported schema.

Keep room-price editing out of event modals. Room management contains only current physical rooms and price management, with two route-based sections: Rooms and Room prices. Reservations has its own sidebar page (`/reservations`), showing stays covering the fixed current business date. Hotel configuration has its own sidebar page (`/hotel-configuration`), with expanded room types, inventory, capacities, area, base rates and facilities. These pages use the shared toolbar hotel scope, without operational date filters. Do not put reservation or room-type sections back below the room inventory. Pricing is independent of events: choose a hotel, room type and any inclusive interval in the complete October–December calendar, inspect current dated selling rates, then apply one new nightly rate. One-day, cross-month and past-date intervals are supported. The optional reason can reference an event; it never limits dates or availability of pricing. Event actions may prefill a hotel/interval/reason, but every field remains editable. Current rates combine canonical roomRates with local overrides; later updates win on overlapping dates, persist on this device and leave booked revenue unchanged. Legacy event proposals migrate to local dated updates without deleting their original storage. Rooms and reservations always show the current business date, independent of analytics selections. Pricing interval inputs belong to the rate-editing task, not the page header. Legacy /room-prices links redirect to the integrated price section. Kassandra estimates use the current selling rates with the local relevance/occupancy rule. Never present application selling-rate changes as published PMS rates. Preserve the distinction between fixture event assessments and live chat analysis.

Room prices includes an Apache ECharts timeline covering the full enclosing calendar months of the From–Through interval, within the available October–December calendar. Show a fixed 10-day window with a keyboard-accessible scrollbar. Center selections up to 10 days where month boundaries allow; longer selections start at From. Outside dates show the computed average booked price as a light gray line only, without dots or patterned backgrounds. Light purple dots inside the interval show each distinct nightly price actually accepted by existing bookings for that stay date, with booking counts in the tooltip. They are booked-price scatter points, not current selling quotes. Keep fixture pricing simple: most occupied room-type/day records have one accepted price, occasional dates have two or three, and no fixture date has more than three. Every distinct accepted price must remain visible; simplify the source bookings rather than dropping chart points. The rounded purple line is booked room-night revenue divided by accepted booked room nights for that stay date, with repeated prices weighted by the number of booked rooms. A day with one distinct booked price must have its average exactly at that dot. Its gray continuation uses the same calculation outside the interval; the vertical axis includes all plotted booked prices and averages and stays fixed while scrolling. Exclude cancelled, pending, no-show, unassigned and not-yet-booked reservations; days without bookings have no dots and null average gaps. Future averages reflect existing reservations only. Local selling-rate edits update the current-rates table and editor, leaving booked-price dots, averages and scroll position unchanged. Keep the selected room type/hotel consistent across chart, table and editor.

Room-price From and Through calendars commit and close immediately on day selection, with no Cancel or Apply buttons; retain validated Enter submission for typed dates. Keep all three pricing selectors on one row when they fit. At narrow content widths, Room type spans the full first row and From/Through share the next row, with readable compact date controls. The single-column pricing layout shows Update rates immediately after the selectors, then Price history and Current rates; keep the desktop analysis-left, update-right layout. Event-modal footers contain only their right-aligned Edit prices and Update with Kassandra actions, wrapping on narrow screens without explanatory footer text.

Current Rooms includes scoped Available, Needs cleaning, Out of service and Reserved cards that filter the inventory. Row Actions can mark clean/dirty, reserve a free room, take it out of service, return it to service, or reset local changes. `RoomOperationsService` exposes API-confirmed current-business-date overrides; the mock repository persists them under `juyo.room-operations.v1`; canonical fixture room states, accepted bookings and financial history remain immutable. Reserved is a manual hold, not a guest booking. Occupied rooms allow housekeeping changes but cannot be freed, held or blocked while their booking remains. Operational inventory, warnings, current-day facts and price availability use the overlay; broad period analytics retain their canonical ledger basis. Held rooms reduce free inventory and remain separate from booked rooms: available + booked + held = sellable. Out-of-service rooms are excluded from sellable capacity. Popup availability notes manual holds when present. Failed storage must not publish a change. Keep filter counts, pagination and focus correct when an action removes a row from the active queue.

Follow the supplied compact analytics reference: an inset white sidebar, light gray workspace (`#f3f4f3`), white task surfaces, dark ink (`#1b211f`), Juyo purple data accents (`#9d8df1`) and fine neutral borders (`#e7eae7`). Use the official hover purple `#865cc8`, derived dark purple `#6442a6` for readable accent text and focus, and pale purple selection surfaces. Keep comparison bars gray and warning/error statuses meaningful. Shared CSS tokens live in `src/styles.css`; resolved ECharts colors live in `src/app/shared/chart-colors.ts`. Use locally bundled DM Sans, compact medium-weight headings, readable tabular numbers, and 10–14px corners. Use `--muted` (`#69716c`) for small supporting text; reserve the quieter `--quiet` (`#777d78`) for nonessential details.

The price-chart hover popup is a compact summary above the cursor, showing the weighted average, booking total and dated room-type availability without a price list. Clicking a chart date opens the full price breakdown and pins that date until an outside click or Escape; moving the cursor must not replace or dismiss it. Clicking another date replaces the pinned date. The full breakdown uses the same booked-price buckets as the dots and shows every price with its booking count. Clear stale pinned details when the hotel, room type, interval or chart window changes. Free rooms are one shared inventory across prices, excluding out-of-order rooms; never invent a separate quota for each historical price. Long price lists scroll with sticky headings and totals. Keep the popup inside the viewport, usable by touch, dismissible with Escape/outside interaction, and mirrored by the keyboard-accessible Daily prices table. Popup HTML comes from the escaped formatter in `room-price-tooltip.ts`; its global CSS must stay namespaced.

Use lighter purple (`#c7b8f2`) for on-the-books revenue and its legends/progress segment. Today is an ordinary row in the same option list as the months; do not add a This month shortcut. In period view, the revenue chart includes the full enclosing calendar month or months: days outside the selected interval show only gray patterned target-height bars, with no revenue values, tooltips or date-selection actions. These context days never contribute to dashboard metrics. A single-month view shows all 30 or 31 days without scrolling; multi-month views show 30 days at a time through one horizontal scrollbar below the chart, with keyboard access and a fixed vertical axis.

The revenue card is titled “Total revenue for the day” in day view, including local drill-downs, and “Total revenue for the time interval” in period view. Hide the lowest-dates opportunity card for single-day filters; keep its period context during local drill-downs. A single-day filter shows day facts in the revenue card instead of the chart: occupancy, rooms to sell (unsold rooms for past dates), average rate, out-of-order rooms, arrivals and departures. Counts reconcile to the dated room inventory and accepted assigned-room reservations; arrivals/departures count rooms, not guests. Keep the daily revenue target. Clicking a chart bar opens the same daily view inside Room revenue without changing the applied filter or other cards. Back restores the applied period and preserved chart position. Applying a new date filter clears this local drill; changing hotel preserves the inspected day. Never show a separate Daily section below Target. Do not show a View dates disclosure or daily data table in the revenue card; the period chart leads directly into Target. The reporting calendar supports selecting a single day with the keyboard.

The fixed business date is November 14, 2026, with November 7 as the pickup comparison. A shared reporting month controls October, November and December analytics. Room management always uses the fixed current business date, without operational date filters. Overview additionally supports Today and inclusive custom date ranges, including one day and cross-month intervals, through a Taiga calendar popup. All dashboard revenue, targets, occupancy, chart rows and hotel comparisons use the selected range. Custom dates apply only after Apply; Cancel, Escape and outside dismissal discard edits. Available dates are October 1 through December 31, 2026. Exact whole-month selections update the shared month; custom ranges preserve the other views' month and date. Dates before November 14 are actuals; today and later have on-the-books room revenue, scheduled room states, planned costs and planned ancillary activity. Actual operating profit uses actual revenue and actual costs only. Pulse today's outline only when the selected range includes today, with reduced-motion, visibility and offscreen guards. Pale target gaps are planning gaps, never forecasts. Period totals are room nights, not physical rooms. Kassandra uses the same selected month/date or explicit dates in a question, and saved fixture answers refresh when the dataset version changes.

The reporting calendar uses white text on dark purple for selected endpoints and Apply. Saturday/Sunday columns have a very light gray background with normal ink, without red dates or underlines. Calendar-specific Taiga inner-DOM overrides live in the globally imported, namespaced `reporting-calendar.css`. Date cells must remain one stable hit target over both their numerals and padding: prevent calendar text selection and keep decorative range layers and markers out of pointer hit testing.

The Occupancy card plots a compact Apache ECharts line of daily sold/booked rooms divided by sellable rooms, using only dates in the applied interval. Stayed and Booked percentages sit side by side below it, separated vertically; one-sided periods show Stayed or Booked beside Target. Retain the useful occupancy target, remove average-rate rows and their horizontal separator, and keep this card on the applied period during Revenue drill-downs. A one-day range is one plotted point; zero-capacity days have a null gap rather than an invented occupancy.

The lowest-dates opportunity card sits horizontally below Revenue in the left column, with responsive stacked rows on phones. Booking sources occupies the right rail below Occupancy. Its ECharts bars show each channel's share of distinct accepted reservations with a stay night in the applied inclusive date interval, not reservations created during that interval. Count a multi-night booking once; tooltip room nights and revenue include only selected stay dates. Both hotel scope and single-day filters apply. Keep sources on the applied interval during a local Revenue day drill-down. Preserve zero-count sources and show a concise No bookings state instead of an empty chart when all counts are zero.

Keep the first viewport useful: real hotel KPIs, a dominant performance chart, and supporting capacity, channel and property comparisons. Every dashboard figure must derive from the canonical fixture. Preserve concise labels and a clear selected hotel scope. The login remains limited to the logo and sign-in form.

Use Tailwind utilities for straightforward layout, spacing and responsive behavior, with scoped CSS for the product's specific charts and controls. Tailwind preflight is deliberately omitted to preserve Taiga UI behavior. All selection dropdowns use the reusable `AppSelectComponent` in `src/app/shared/select.component.ts`, built with Taiga UI 5; do not add native selects or a second dropdown implementation. Keep icon glyphs purpose-drawn and local.

Use Angular 22 `animate.enter` / `animate.leave` for brief state transitions, alongside proportionate focus and hover feedback. Prefer these native APIs over the legacy Angular animations package. Respect reduced motion and keep keyboard access, Escape dismissal, focus return, and scrollable data tables working.

# API ownership

All runtime business data and persisted domain changes go through typed Angular HttpClient services under `core/api/` or their domain facades. HTTP is the default; the lazy browser-local mock interceptor is available only through the explicit mock configuration. Do not import `network.data` or generated fixture replies in components, stores or live frontend services. Fixture access and mock browser persistence belong only to mock repositories and offline scripts. Pure calculations accept an API snapshot.

The standalone backend owns SQL access, authorization, input validation and durable writes. Canonical `juyo` facts are read-only; API-owned changes live in `juyo_api`. The email/password sign-in endpoint compares plaintext credentials against the backend-only hardcoded demo catalog, without password hashing. Reject invalid credentials before SQL access; preserve enabled persistent identities and per-user conversation predicates. New demo identities store no database password; migrations preserve existing account IDs, legacy rows and history. Sessions remain opaque bearer tokens whose SHA-256 hashes are stored in SQL. Never import the demo catalog into Angular, API responses or hotel exports. All provisioned users currently share one hotel workspace. Live chat uses the configured server-side OpenAI Responses integration and authenticated MCP tools; no PMS integration exists. OpenAI credentials belong only in the separate Kassandra Worker secret configuration or process environment, never Angular, source, reports or logs. HTTP browser sessions retain only the opaque token, not user profiles or passwords, and do not use cookies. Keep credentials out of URLs/logs. The Worker SQL adapter pins mssql/Tedious behavior, verifies TLS certificates/hostnames, and isolates its connection hook in one file; verify that adapter and actual SQL behavior before dependency upgrades.

Authentication restores identity only. The protected-shell resolver loads the small ReferenceDataService hotel/calendar catalog before shell activation. Each page then loads only its scoped resources through NetworkDataStore and ResourceQueryStore. Never call `/exports/network` for frontend startup or navigation. The active page read model is explicitly partial; keep unused collections empty and expose only valid page calculations. Overview needs selected-scope booking positions and nights plus compact organization positions for its visible comparison; day inventory/arrivals/departures load on drill-down. Management uses the business date. Configuration loads one hotel's types. Prices load selected-type rates/history over enclosing chart months, with hotel/date-scoped room states. Shared notification lists support network counts; event pricing details are lazy and independent of the active page.

Use NgRx for reference metadata, resource cache entries, active page status, notifications and operational overlays. Resource cache keys include resource/hotel/date/type, have a finite TTL and entry bound, coalesce in-flight reads and never persist financial data to browser storage. Cancel obsolete requests and guard late completions; publish complete scoped page data atomically. Shared operational overlays initialize only when needed. Confirmed room edits invalidate merged daily details without unmounting controls; rate edits update overlays while accepted booking history remains canonical. Preserve retryable errors, overall read deadlines, pagination limits, inclusive stay-date semantics and no automatic write retries. Clear session-owned caches after authenticated views are destroyed. Keep schema metadata available to backend MCP/tools without a frontend schema-page request. Do not serve `public/data` as an API bypass.

Backend DTO/calculation copies under `backend/src/domain` are intentional: the backend is independently deletable, and the frontend can revert to explicit mock mode. Synchronize both copies for contract or calculation changes and run the independent SQL readback/domain/API checks. See `backend/README.md`, `docs/api.md` and `docs/openapi.json`.
