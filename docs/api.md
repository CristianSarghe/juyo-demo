# API boundary

All application data crosses Angular services and `HttpClient`. The default HTTP transport targets `https://api-juyo.cristiansarghe.com/api/v1`. The standalone backend reads the existing SQL Server and persists API state separately. The Angular frontend supports local development and the authorized Cloudflare Pages Free deployment at `https://juyo-demo.pages.dev`; it contains no SQL driver, credentials or direct database connection.

[OpenAPI 3.1 contract](./openapi.json) lists request/response schemas and operations. Regenerate it with `npm run docs:api`. Resource paths live in `src/app/core/api/resource-paths.ts`; business DTOs live in `network.models.ts`, `api.models.ts` and `mutation.models.ts`.

## Ownership

- `ApiClient`: bearer authorization, safe versioned URLs, query encoding, bounded pagination, retry/deadline policy and normalized errors. Writes never retry automatically.
- `ReferenceDataService`: shared NgRx hotel/calendar catalog, loaded by the protected-shell resolver. Authentication does not load page data.
- `AppUiStore`: selected hotel and reporting context. Router query parameters remain the authority for page, pricing dates and room type.
- `ResourceQueryStore`: session-only NgRx cache of typed resource reads, keyed by resource and sorted scope/date/type filters. It coalesces identical requests, expires after 60 seconds and retains at most 48 entries. No financial responses are persisted in browser storage.
- `NetworkDataStore`: the active scoped page read model, its request key/loading/error state and a separate bounded day-detail cache. It cancels obsolete reads, publishes atomically and rejects late responses. Unrequested collections remain empty and must not be interpreted as a complete network snapshot.
- `NetworkService`: the page's domain queries and shared reference access. Header counts do not call financial summary calculations.
- `NotificationsStore`: small shared portfolio warning/event lists for selected/total header counts. Event pricing details and warning type labels load on demand, independently of page data.
- `RoomOperationsService`, `RoomRateService`, `AuthService`, `ChatService`: shared API-backed NgRx facades for operational overlays, identity and conversations. Drafts, focus, chart position and popovers stay local.
- `backend/`: SQL queries, authorization, validation, sessions and durable room/rate/chat writes. Its domain copies remain independently removable.
- `api/mock/`: explicit offline interceptor and fixture repositories. HTTP mode never falls back to fixtures.

The protected shell resolver loads only `GET /reference-data` after the session guard succeeds. Page content then loads for the selected hotel and relevant dates, with its own skeleton, error and retry state. Switching filters cancels stale page requests; switching pages reuses matching resource entries. Page components have separate lazy JavaScript bundles. The frontend never calls `/exports/network` during startup or navigation.

| Page/task           | Requested data                                                                                                                                                                                                                                                                                       |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Overview            | Selected hotel's booking positions and accepted reservation nights for the reporting interval; enclosing-month positions supply the chart context. Compact position rows for all hotels in the applied interval support the visible organization comparison. Room types supply physical room counts. |
| Revenue day detail  | Only after selecting a day: scoped rooms, that day's states/positions, and reservations overlapping the previous night and selected day so departures are included. Current-day operational changes are merged separately.                                                                           |

Shared operational/rate overlays initialize when room management first needs them.                                                                                                 |

Canonical reporting facts remain separate from operational overlays. Confirmed room edits invalidate merged daily details without unmounting the active controls; rates update their NgRx overlay without changing accepted booked prices/history. Logout clears catalog, page, query, notification and overlay caches after authenticated views are destroyed. Individual resource requests retain pagination bounds and an overall timeout including transient retries.

## HTTP contract

IDs are opaque strings. Available dates, reporting months and business date come from the shared authenticated `/reference-data` catalog. Clients must not infer IDs or hardcode fixture date bounds. Dates are ISO `YYYY-MM-DD`; timestamps are ISO date-times. Monetary amounts are EUR excluding VAT; percentage outputs use 0–100, commission fractions use 0–1.

Hotels include nullable `address: { line1: string, line2?: string, postalCode: string }` in hotel, reference-data and snapshot responses. City/country and coordinates remain separate fields. SQL reads the optional one-to-one `juyo.HotelAddress`; API requests cannot modify it. The configured sample addresses describe fictional properties, and coordinates are illustrative rather than verified address matches.

Collection responses use `{ items, page, pageSize, total }`. Pages are one-based, default size 50, maximum 1,000. The collection client requests 500 rows and rejects inconsistent totals or more than 50,000 rows per collection; each page requests only its required scoped collections. Source ordering is stable; no sorting parameter is currently exposed.

Omitting `hotelId` means all hotels authorized for the workspace. `from` and `to` are inclusive and must be supplied together. Daily records filter their stay/reporting date; monthly rows use enclosing months. Reservation/event intervals overlap the selection; `stayDate` uses `arrival <= stayDate < departure`. Unsupported collection query names return 400. Filters relevant to each resource are listed in OpenAPI.

A room action is `clean`, `dirty`, `reserve`, `out_of_service`, `available` or `reset` (DELETE is preferred for reset). An occupied room cannot be freed, held or blocked while booked. A manual reservation is a hold, not a guest booking. Writes publish client changes only after success; blocked persistence leaves the previous state intact.

Rate requests contain `hotelId`, `roomTypeId`, `startDate`, `endDate`, `nightlyRate`, and optional `eventId`/`reason`. Later applications win on overlapping dates; events never constrain dates. `/room-rates` returns effective selling quotes by default; `basis=canonical` returns immutable base quotes used by the reporting cache. Selling-rate updates never rewrite accepted reservation revenue or booked-price history. Average booked price is accepted selected-night revenue divided by booked room nights, with a null gap when none exist.

Conversation history retains at most 30 conversations per user and 100 messages per conversation. Creating a conversation supplies `title`, `propertyId` (hotel ID or `portfolio`), `month` and `roomDate`. A message optionally carries `context: { propertyId, startDate, endDate }`, reflecting the current hotel and inclusive dashboard range. Explicit dates in a question do not change the global filters. The server commits the question/answer together. HTTP answers come from OpenAI Responses with authenticated MCP tools; the explicit offline fixture adapter retains deterministic replies. Responses are cloned at the mock HTTP boundary. Stopping a response unsubscribes its request and guards against stale scope/date publication; a live backend may already have accepted a cancelled write. HTTP GET requests retry transient network/502/503/504 failures at most twice, after 300 ms and 600 ms. Authentication/validation/other client failures are not retried. No write receives an automatic retry. A cancelled mock request performs no mutation if cancelled before its handler executes. Chat has a bounded 180-second client timeout; ordinary API and confirmed-write timeouts remain unchanged.

Assistant messages may include `webSources: { url, title }[]` and `citations: { url, title, startIndex, endIndex }[]`, where offsets refer to the returned plain-text content. These bounded, validated HTTP(S) links persist in the existing versioned message payload and restore with history. The UI renders inline source links and an expandable source list.

For repairs, authenticated `get_hotel_repair_context` supplies the selected hotel's configured address/coordinates, current room faults, maintenance notes, facility context and missing information. `find_repair_providers` is a separate bounded server-side function: public web search receives only an allowlisted trade and trusted city/country, never hotel names, exact addresses, room notes, guests, bookings, credentials or conversation history. Results cite publicly listed business phones and service areas without claiming confirmed availability or arranging a visit. Search does not contact providers or change room state. Any requested room/rate change still becomes a pending proposal requiring the app's Apply button.

An assistant message may include `action: { id, kind, status, summary, details }`. `kind` is `rate_batch_update`, legacy `rate_update`, or `room_action`; `status` is `pending`, `applied` or `cancelled`. Batch details contain `updates` (1–20): each row has the rate-update request, hotel/type names, current minimum/maximum selling quote and an opaque `expectedRateVersion`. Inclusive intervals for the same hotel/type must not overlap. The server locks room types in stable order, verifies every dated quote fingerprint and applies all rows plus the message decision in one transaction. A changed quote rejects the entire batch with `409 STALE_RATE_PROPOSAL`; no partial rate writes occur. Legacy single-rate details contain the existing rate-update request plus `hotelName`/`roomTypeName`; room details contain `roomId`, `hotelName`, `roomNumber`, `action` and `date`. MCP can stage a proposal, but cannot apply it. Apply/Cancel sends only the decision for the server-stored action. The owner-scoped confirmation transaction applies the change and status atomically. Same-decision retries return the existing result without another write; opposite decisions return `409 CHAT_ACTION_ALREADY_DECIDED`. Room actions also reject stale business dates and occupied-room conflicts. After application, the frontend refreshes the relevant overlay without clearing the published cache. The explicit offline adapter supports the same event batch review/decision workflow, with one atomic rate-storage write and idempotent history-save recovery.

Failures use `application/problem+json`: `{ type, title, status, detail, code, errors? }`. Typical statuses: 400 invalid query/JSON, 401 anonymous or invalid credentials, 403 rejected browser origin, 404 missing resource, 405 unsupported method with `Allow`, 409 room-state conflict, 413 excessive body/history, 415 wrong content type, 422 invalid body, 429 login throttled, 503 unavailable persistence. Throttled responses include `Retry-After`. Mock unexpected errors may use 500. `ApiError` normalizes these and exposes status/code; client timeout/network failures use status 0. Error text is shown through existing form/load states; rejected writes preserve the prior client cache. An HTTP transport failure can occur after a server commit, so refresh state before manually retrying a write.

## Sessions and transport modes

HTTP sign-in accepts `{ email, password, remember? }` and compares credentials directly with the backend-only hardcoded demo account catalog. Passwords are intentionally plaintext demo values; login performs no password hashing or database password lookup. Invalid credentials are rejected before SQL access. The corresponding SQL identity must be provisioned and enabled; sign-in returns `{ user, token }`. See [demo accounts](../backend/README.md#authentication). The catalog is never imported into Angular or included in API responses or hotel exports.

Send the opaque token in `Authorization: Bearer …`; `GET /sessions/current` returns only `{ user }`. Tokens expire after one day, or 30 days when remembered. SQL stores SHA-256 token hashes; new demo identities store no database password. The additive migration preserves existing user IDs, legacy account rows and history. Logout deletes the supplied token if present and returns 204 for absent/expired tokens too.

The browser stores only the opaque token in session storage, or local storage with Remember me, scoped to the configured API base URL. Authorization is attached only to API resource requests; a delayed 401 cannot invalidate a newer token. Requests use `withCredentials: false` without session cookies. The backend checks enabled users, confines conversations to their owner, and limits browser origins to the configured allowlist. All provisioned accounts currently access the same hotel workspace; hotel filters are query scope, not separate account permissions.

`src/environments/environment.ts` selects HTTP by default using `HTTP_API_CONFIG`. The explicit Angular `mock` configuration selects `MOCK_API_CONFIG`:

```sh
npm start -- --configuration mock
npx ng build --configuration mock
```

The mock interceptor simulates routes in the browser; it does not create a listening server or make mock routes available to `curl`/plain `fetch`. Mock sign-in accepts validly formatted local credentials, returns `{ user }` without a bearer token, and keeps its own local session. Its room/rate/chat stores are independent of SQL; passwords are never persisted. Responses are cloned, and requests cancelled before mock handler execution perform no mutation. HTTP mode bypasses the interceptor and uses the actual endpoint.

## Backend operation

The configured standard Cloudflare Worker uses mssql 12.7.14/Tedious 20.3.9 over directly established, certificate-verified strict TLS with a 16,000-byte TDS packet. The connection-instance adapter is isolated in `backend/src/sql-worker-transport.ts`. Large message text is staged in bounded Unicode pieces on the same SQL transaction before the final constrained write; API payload limits and atomic Apply behavior remain unchanged. It uses no paid features, Containers or D1 and does not host the frontend. The same handler runs on Node; see [backend setup](../backend/README.md) for environment variables, secrets and checks.

The backend reconstructs canonical `juyo` facts from normalized tables/views. Reference data uses a dedicated small read; resource filtering and pagination happen in SQL. Derived reports use a decoded snapshot cached for 30 seconds. RPC batches stay small for the Worker TLS transport, and full snapshots retain one consistent transaction. The separately applied, additive `juyo_api` migration owns eight tables for auth, state/audit and conversations. Room/rate writes never modify accepted booking prices or financial history. Kassandra uses a separate small Cloudflare Free Worker (`juyo-kassandra`) at `https://mcp-juyo.cristiansarghe.com`. Its `/mcp` endpoint exposes authenticated data and proposal tools; `/chat` handles model inference through OpenAI Responses. The API forwards chat through `KASSANDRA_URL`; `OPENAI_API_KEY` is a secret on the Kassandra Worker only. Its non-secret bindings are `JUYO_API_URL`, `MCP_PUBLIC_URL` and `ALLOWED_ORIGINS`. The model is `gpt-6.1-terra` with low reasoning effort. Inference, bridge and Angular message deadlines are 160/170/180 seconds; MCP-only reads retain 75 seconds, and cancellation propagates through request signals. The thin Worker calls the existing authenticated API and has no SQL driver, database, Durable Object or paid Cloudflare feature. See [MCP implementation](../backend/docs/MCP.md) for tool coverage and deployment details. Backend DTO/calculation copies are intentional so the backend can be removed independently and the frontend reverted to explicit mock mode.

Verification: frontend `npm run test:api` exercises the mock HTTP boundary; `test:api:facades` and `test:session` cover cancellation, failures, session races and cache reset. Backend `npm test` covers chat behavior and includes the opt-in SQL integration test. `npm run db:verify` independently reads back every canonical property; `SQL_INTEGRATION=1 npm test` exercises actual SQL persistence and rollback with temporary API-only users, then checks unchanged canonical facts. Neither a bundle nor a local Worker test proves public deployment availability.

The existing REST custom domain previously passed live HTTPS and persistence checks on 14 November 2026. Those checks predate the MCP/OpenAI integration and do not establish its deployment status. Verify the MCP handshake, a real model-backed data question and confirmation behavior after deploying the new Worker. No paid Cloudflare feature or hosted frontend is needed.
